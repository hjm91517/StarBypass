# CI：用 GitHub Actions 构建

## 为什么值得走这条路

本地构建（`make cross`）是在没有 iOS SDK 的环境里硬凑出来的，代价是一串补丁：

| 本地做的手工补救 | 真 SDK 下的状况 |
|---|---|
| 链接后手工注入 4 条 `LC_LOAD_DYLIB` | 链接器自动生成，不需要 |
| `-no_fixup_chains` 规避 chained fixups | 有 `-Wl,-no_fixup_chains` 显式声明，语义清晰 |
| `compat/` 一堆桩头文件 | 完全不需要，用官方 SDK |
| `ld64.lld` 交叉链接 | `xcrun clang` 原生链接 |
| 无法验证 ARC 兼容性 | 真机 ABI + ARC 一次编译验证 |

**真 SDK 构建是唯一能同时验证「能在 arm64 iOS 上编译并正确链接」的方式。**

## 工作流内容

文件：`.github/workflows/starbpass-build.yml`

```yaml
on: [push, workflow_dispatch]
runs-on: macos-14          # Apple Silicon，自带 Xcode
```

九个步骤：

1. `actions/checkout@v4` — 取代码
2. 打印 Xcode / SDK / clang 版本
3. `python3 docs/verify-contracts.py` — 契约一致性
4. `xcrun -sdk iphoneos clang ... -fobjc-arc -dynamiclib` — 真机构建
5. `python3 src/tools/verify-binary.py` — 结构校验（`continue-on-error`，失败也留产物）
6. `otool -L` 打出实际依赖，`otool -l | grep __mod_init_func` 确认构造函数
7. `codesign --force --sign -` 临时签名
8. `actions/upload-artifact@v4` — 上传 `StarBypass.dylib`
9. 写 Job Summary

### 关键编译参数

```bash
-arch arm64
-miphoneos-version-min=14.0
-fblocks -fobjc-arc -O2
-dynamiclib
-install_name @executable_path/Frameworks/StarBypass.dylib
-framework Foundation -framework UIKit -lobjc -lSystem
-Wl,-no_fixup_chains
```

**为什么用 `-fobjc-arc` 而不是本地验证过的 `-fno-objc-arc`：**

`03-network.m` 里替换 `completionHandler` 时，包装块捕获了 `req` 和 `handler`。
MRR 下 block 不会持有捕获的对象，请求返回时可能已被释放 → 野指针崩溃。
ARC 下自动持有，安全。源码中没有任何 `retain`/`release`/`dealloc` 调用，本身就是 ARC 兼容写法。

## 当前阻塞：Token 权限

已实测该 token 的权限边界：

| 操作 | 结果 |
|---|---|
| 读用户信息 | 200 通过 |
| 读仓库列表 | 200 通过 |
| 读 Actions 工作流 | 200 通过 |
| **创建仓库** | **403** `Resource not accessible by personal access token` |
| **写文件内容** | **403** 同上 |
| **触发工作流** | **403** 同上 |

这是**细粒度 PAT 未授予写权限**，不是代码或网络问题。
`/user/repos` 返回的 `permissions.push=true` 表示账号本人的权限，不代表该 token 的权限。

### 需要补齐的权限

在 GitHub → Settings → Developer settings → Fine-grained tokens → 该 token → 编辑：

| 权限 | 级别 | 用途 |
|---|---|---|
| **Contents** | Read and write | 推代码、建分支 |
| **Workflows** | Read and write | 提交 `.github/workflows/` 下的文件 |
| **Actions** | Read and write | 触发、下载 artifact |
| **Administration** | Read and write | 新建仓库（若要用 API 建库） |

Repository access 需包含目标仓库（或选 All repositories）。

> 注意：只想让 CI 跑起来，最少需要 **Contents: write + Workflows: write**。

## 权限到位后的执行步骤

```bash
cd /workspace

# 1. 建仓库（或手动在网页端建好后跳过）
curl -X POST -H "Authorization: Bearer $TOKEN" \
  -H "Accept: application/vnd.github+json" \
  https://api.github.com/user/repos \
  -d '{"name":"StarBypass","private":true}'

# 2. 推送
git remote add origin "https://x-access-token:$TOKEN@github.com/hjm91517/StarBypass.git"
git push -u origin main

# 3. 等 Actions 跑完，下载 artifact
curl -H "Authorization: Bearer $TOKEN" \
  "https://api.github.com/repos/hjm91517/StarBypass/actions/runs?per_page=1"
```

也可以不建新库，推到已有仓库的新分支（不触碰 `main`）：

```bash
git push origin main:starbpass
```

工作流触发器是 `on: push`（全部分支），推任意分支都会跑。

## 拿不到 artifact 时的替代

在自己的 Mac 上一条命令即可，效果等价于 CI：

```bash
cd src && make ios
```

产出 `src/StarBypass.dylib`，同时会执行 `file` 打印架构。

## 构建失败怎么读日志

工作流把校验结果写进 Job Summary。按顺序看：

1. `Show toolchain` — 确认 SDK 版本，排除环境问题
2. `Build StarBypass.dylib` — 编译错误会在这里，直接看 clang 报错行
3. `Verify binary structure` — 结构问题，看 PASS/FAIL 明细
4. `Show load commands` — 依赖和构造函数是否如预期

若第 2 步报 `-fobjc-arc` 相关错误，说明有 MRR 写法漏进源码，按报错行改。
